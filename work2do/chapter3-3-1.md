# chapter3-3-1

## 实验目标与假设

本实验的核心目标是验证以下三个核心假设：

1. **H1****（I/O效率）**：在相同的召回率（Recall@k）水平下，Ours方法能够显著减少单次查询所需的磁盘读取次数（Page Reads per Query）和I/O数据量，证明聚类策略有效提升了块级局部性。
2. **H2****（抗退化能力）**：在长期的动态插入与删除混合负载（Long-term Dynamic Workload）下，Ours方法的搜索延迟（尤其是P99延迟）和吞吐量（QPS）能够保持稳定，不发生类似基线系统的显著性能衰减。
3. **H3****（微观架构增益）**：Ours方法能够提高操作系统的页缓存命中率（Page Cache Hit Rate）和CPU缓存效率（LLC Hit Rate），从而降低系统的整体能耗和资源占用。

## 实验环境配置

为了确保实验结果的可复现性和公平性，我们将采用标准的服务器硬件配置，并严格控制软件环境，特别是I/O栈的配置。

#### 数据集

实验将采用业界公认的十亿级高维向量数据集，涵盖不同维度、数据分布特征和模态，以验证方法的通用性。

| **数据集**        | **向量数量** | **维度** | **数据类型** | **距离度量**  | **特征描述**                                           |
| ----------------- | ------------ | -------- | ------------ | ------------- | ------------------------------------------------------ |
| **SIFT1B**        | 10亿         | 128      | uint8        | 欧氏距离 (L2) | 计算机视觉特征，分布相对均匀，标准基准 1。             |
| **Deep1B**        | 10亿         | 96       | float32      | 欧氏距离 (L2) | 深度学习特征，簇状分布明显，适合测试聚类策略的适应性。 |
| **MSTuring-100M** | 1亿          | 100      | float32      | 欧氏距离 (L2) | 文本语义向量，用于模拟RAG场景下的真实负载 1。          |

#### 基线系统 (Baselines)

为了凸显本文方法的优势，我们将选取代表不同技术路线的最先进系统进行对比：

1. **DiskANN (Vamana)**: 代表传统的静态磁盘图索引。我们将测试其在经历模拟更新后的性能（即不进行优化，直接追加写入），作为“无优化”的对照组。
2. **FreshDiskANN**: 代表“缓冲-合并”策略的SOTA系统。实验将重点关注其在合并（Merge）操作发生时的性能抖动和I/O风暴。
3. **IP-DiskANN**: 代表现有的“原地更新”策略。该系统支持动态更新但缺乏物理布局优化，是本文方法最直接的竞争对手。
4. **PipeANN**: 代表基于流水线优化的最新系统。虽然PipeANN主要优化搜索算法，但其对I/O延迟的处理与本文的布局优化有互补性，对比可揭示布局优化的独立贡献。

## 3. 实验内容与流程

实验将分为三个主要阶段：长期稳定性测试、I/O效率深度分析、以及系统微观指标剖析。

#### 实验一：长期动态更新下的性能稳定性 (Long-Term Stability Test)

**目的**：验证假设H2，即动态聚类策略在抑制图索引物理退化方面的效果。

**流程**：

1. **初始化**：使用数据集的前50%（如SIFT1B的5亿向量）构建初始索引。
2. **混合负载注入**：模拟真实世界的流式场景（如推特流或新闻流），运行持续24小时至48小时的混合负载。负载模式设置为：
    **插入率**：1000 - 5000 QPS，模拟高吞吐写入。
    **删除率**：与插入率动态平衡，保持索引总规模在5亿左右波动，模拟滑动窗口（Sliding Window）数据淘汰机制 1。
    **查询率**：保持恒定的背景查询压力（如1000 QPS），用于实时监控搜索性能。

3. **数据采集**：每隔10分钟记录一次系统的关键指标：
    搜索延迟（P99, Average Latency）。
    搜索吞吐量（QPS）。
    磁盘读取带宽（Read Bandwidth）和写入带宽（Write Bandwidth）。

**预期结果**：

●    **FreshDiskANN**：性能曲线应呈现周期性的“锯齿状”跌落，对应其后台合并操作引发的资源争用。

●    **IP-DiskANN**：随着时间推移，搜索延迟应呈现缓慢上升趋势（P99显著恶化），吞吐量下降，反映出物理布局的逐渐碎片化。

●    **Ours**：应呈现出平滑且稳定的性能曲线。P99延迟应显著低于IP-DiskANN，且不出现FreshDiskANN式的剧烈抖动，证明动态聚类和后台重组机制有效维持了索引的健康度。

#### 实验二：搜索I/O效率与放大率分析 (Search I/O Efficiency Analysis)

**目的**：验证假设H1，深入量化3.3.1节中理论分析的I/O增益。

**流程**：

1. 在实验一的终点状态（即经过大量更新后的“老化”索引）下，暂停写入，执行只读基准测试。
2. 使用相同的查询集（10k queries）对各系统进行检索。
3. 调整搜索参数（如Beam Width, Candidate List Size），使各系统达到相同的召回率水平（如Recall@10 = 90%, 95%, 98%）。
4. **指标度量**：
    **平均I/O次数 (Avg I/O Requests)**：完成一次查询平均需要发起的磁盘读取请求数。
    **I/O数据量 (I/O Volume)**：完成一次查询平均读取的磁盘字节数。
    **I/O放大率 (I/O Amplification Factor)**：定义为 $\frac{\text{实际读取数据量}}{\text{有效向量数据量}}$。
    **页内邻居数 (Neighbors per Page)**：平均每个加载的物理页中包含的有效邻居节点数量。这是衡量聚类效果的直接指标。

预期结果：

Ours方法的“页内邻居数”应显著高于基线系统（例如从随机布局的1.2提升至3.0以上），从而导致“平均I/O次数”和“I/O放大率”的大幅下降。我们预期能观察到与BAMG类似的I/O减少效果（如减少40%~50%）1，证明聚类策略成功将随机I/O转化为更加紧凑的访问。

#### 实验三：页缓存命中率与内存带宽测试 (Page Cache & Bandwidth Profiling)

**目的**：验证假设H3，验证动态聚类对操作系统页缓存和内存子系统的友好性。

**流程**：

1. 利用Linux的高级性能分析工具 perf 和 eBPF 工具（如 cachestat, biolatency）监控搜索过程中的内核事件。
2. 设置不同的内存限制（Memory Limit），例如仅提供索引大小的5%, 10%, 20%作为Page Cache，观察性能衰减曲线。
3. **监控指标**：
    **LLC Miss Rate**: Last Level Cache缺失率，反映CPU缓存的利用效率。
    **Page Cache Hit Ratio**: 操作系统页缓存的命中率，直接反映局部性优劣。
    **Page Faults**: 缺页中断次数（Major/Minor）。
    **Instructions per Cycle (IPC)**: CPU指令执行效率，反映是否存在前端停顿。

预期结果：

在内存受限场景下，Ours的性能衰减斜率应显著小于基线系统。由于聚类带来的空间局部性，Ours的Page Cache Hit Ratio应更高。此外，由于更高效的SIMD执行和预取，IPC指标也应优于对比系统，表明计算流水线更加通畅。

#### 实验四：写入吞吐量与并发控制开销分析 (Write Overhead Analysis)

**目的**：评估复杂的动态聚类计算是否会成为写入瓶颈，以及并发控制协议的效率。

**流程**：

1. 逐步增加写入线程数（从1到64），测试系统的最大写入吞吐量。
2. 设置对照组：
    **Group A**: 开启完整功能（动态聚类 + 后台重组）。
    **Group B**: 关闭后台重组，仅进行插入时的简单分配。
    **Group C**: 随机分配物理位置（模拟IP-DiskANN行为）。

3. 记录写入操作的平均延迟分布，并分析锁竞争（Lock Contention）情况。

预期结果：

虽然动态聚类增加了插入时的计算量（寻找最佳聚类页），但由于基于前缀的划分减少了锁竞争 1 且减少了I/O阻塞，整体写入吞吐量应仍具竞争力。特别是与FreshDiskANN相比，Ours应能提供更平滑的写入延迟，不会出现因合并导致的写入停顿（Write Stall）
